# Database Architecture

## Objectives

The replacement SQLite model must support durable workspaces, provider accounts, branching conversations, structured message parts, citations, attachments, tools, run metadata, and FTS5 search. It must also import the existing two-table database without data loss.

## Principles

1. Stable IDs are generated by the application, never array indexes.
2. Conversation history is a graph, not a permanently linear array.
3. Messages and message parts are normalized enough to query and render safely.
4. Provider-specific metadata is isolated and namespaced.
5. Schema changes use numbered migrations.
6. Repository APIs own SQL; UI and provider adapters never execute SQL.
7. Multi-row domain changes are transactional.
8. FTS is a derived index, not the source of truth.
9. Credentials never enter SQLite.

## SQLite configuration

Initial recommendation:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 10000;
```

The Rust database crate should own one managed pool, migration execution, and transaction boundaries. SQLx is the initial recommendation because it integrates with Tokio and embedded migrations; avoid compile-time query macros if they make reproducible CI dependent on a live schema database.

## Conceptual schema

Exact SQL belongs in reviewed migration files. The following defines required semantics.

### `workspaces`

```text
id TEXT PRIMARY KEY
name TEXT NOT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
archived_at TEXT NULL
```

### `providers`

```text
id TEXT PRIMARY KEY
kind TEXT NOT NULL UNIQUE
name TEXT NOT NULL
adapter_version TEXT NOT NULL
capabilities_json TEXT NOT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

Capability JSON is provider registry metadata, not a message payload. It is schema-versioned.

### `provider_accounts`

```text
id TEXT PRIMARY KEY
provider_id TEXT NOT NULL FK providers
label TEXT NOT NULL
credential_ref TEXT NOT NULL UNIQUE
status TEXT NOT NULL
masked_identifier TEXT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
last_validated_at TEXT NULL
```

`credential_ref` points to OS secure storage. It is not the token.

### `models`

```text
id TEXT PRIMARY KEY
provider_id TEXT NOT NULL FK providers
provider_model_id TEXT NOT NULL
name TEXT NOT NULL
capabilities_json TEXT NOT NULL
enabled INTEGER NOT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
UNIQUE(provider_id, provider_model_id)
```

### `conversations`

```text
id TEXT PRIMARY KEY
workspace_id TEXT NOT NULL FK workspaces
provider_id TEXT NOT NULL FK providers
provider_account_id TEXT NULL FK provider_accounts
title TEXT NOT NULL
active_branch_id TEXT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
archived_at TEXT NULL
```

A deferred migration or repository invariant can establish the `active_branch_id` foreign key after branch creation to avoid insert cycles.

### `branches`

```text
id TEXT PRIMARY KEY
conversation_id TEXT NOT NULL FK conversations ON DELETE CASCADE
name TEXT NULL
forked_from_message_id TEXT NULL
head_message_id TEXT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

A branch names one selected path through the message graph. It does not duplicate all ancestor messages.

### `messages`

```text
id TEXT PRIMARY KEY
conversation_id TEXT NOT NULL FK conversations ON DELETE CASCADE
branch_id TEXT NOT NULL FK branches ON DELETE CASCADE
parent_message_id TEXT NULL FK messages
role TEXT NOT NULL
status TEXT NOT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
edited_from_message_id TEXT NULL FK messages
source_run_id TEXT NULL
```

Roles initially:

```text
system
user
assistant
tool
```

Statuses initially:

```text
pending
streaming
completed
cancelled
failed
interrupted
```

Graph invariant: a message parent must belong to the same conversation. Enforce in repository logic and tests; consider triggers if they remain simple and reliable.

### `message_parts`

```text
id TEXT PRIMARY KEY
message_id TEXT NOT NULL FK messages ON DELETE CASCADE
ordinal INTEGER NOT NULL
kind TEXT NOT NULL
text_content TEXT NULL
mime_type TEXT NULL
attachment_id TEXT NULL
citation_id TEXT NULL
tool_call_id TEXT NULL
metadata_json TEXT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
UNIQUE(message_id, ordinal)
```

Kinds:

```text
text
reasoning
code
image
attachment
citation
tool_call
tool_result
```

`metadata_json` may hold versioned, non-secret auxiliary fields. It must not replace structured columns or contain the whole message.

### `attachments`

```text
id TEXT PRIMARY KEY
workspace_id TEXT NOT NULL FK workspaces
sha256 TEXT NOT NULL
file_name TEXT NOT NULL
mime_type TEXT NOT NULL
size_bytes INTEGER NOT NULL
storage_path TEXT NOT NULL
status TEXT NOT NULL
created_at TEXT NOT NULL
UNIQUE(workspace_id, sha256)
```

Provider file IDs belong in a separate provider mapping table or generation metadata, not in `storage_path`.

### `citations`

```text
id TEXT PRIMARY KEY
conversation_id TEXT NOT NULL FK conversations ON DELETE CASCADE
url TEXT NOT NULL
title TEXT NULL
snippet TEXT NULL
source_name TEXT NULL
retrieved_at TEXT NULL
created_at TEXT NOT NULL
```

Message/part association can use `message_parts.citation_id` or a many-to-many `message_citations` table if one citation appears in multiple places.

### `tool_calls`

```text
id TEXT PRIMARY KEY
message_id TEXT NOT NULL FK messages ON DELETE CASCADE
provider_call_id TEXT NULL
name TEXT NOT NULL
arguments_json TEXT NOT NULL
result_json TEXT NULL
status TEXT NOT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

JSON is appropriate for tool arguments/results because their schema is tool-defined; it is not appropriate as the only message representation.

### `runs`

```text
id TEXT PRIMARY KEY
request_id TEXT NOT NULL UNIQUE
conversation_id TEXT NOT NULL FK conversations ON DELETE CASCADE
branch_id TEXT NOT NULL FK branches ON DELETE CASCADE
provider_id TEXT NOT NULL FK providers
provider_account_id TEXT NULL FK provider_accounts
model_id TEXT NOT NULL FK models
status TEXT NOT NULL
reasoning_enabled INTEGER NOT NULL
search_enabled INTEGER NOT NULL
started_at TEXT NULL
completed_at TEXT NULL
last_event_sequence INTEGER NOT NULL DEFAULT 0
error_code TEXT NULL
safe_error_message TEXT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

### `generation_metadata`

```text
id TEXT PRIMARY KEY
run_id TEXT NOT NULL UNIQUE FK runs ON DELETE CASCADE
input_tokens INTEGER NULL
output_tokens INTEGER NULL
reasoning_tokens INTEGER NULL
duration_ms INTEGER NULL
first_token_ms INTEGER NULL
provider_session_id TEXT NULL
provider_parent_message_id TEXT NULL
provider_status TEXT NULL
adapter_version TEXT NOT NULL
provider_metadata_json TEXT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

Provider metadata must be secret-free and versioned. DeepSeek remote IDs are stored here or in a dedicated provider-session table; they never become application message IDs.

### `settings`

```text
scope TEXT NOT NULL
scope_id TEXT NOT NULL
key TEXT NOT NULL
value_json TEXT NOT NULL
updated_at TEXT NOT NULL
PRIMARY KEY(scope, scope_id, key)
```

Scopes can include application, workspace, and account. Settings are durable preferences, not active UI state.

## FTS5 design

Use explicit FTS5 indexes for conversation titles and searchable text parts.

Conceptual tables:

```sql
CREATE VIRTUAL TABLE conversation_fts USING fts5(
    conversation_id UNINDEXED,
    title,
    tokenize = 'unicode61 remove_diacritics 2'
);

CREATE VIRTUAL TABLE message_part_fts USING fts5(
    part_id UNINDEXED,
    message_id UNINDEXED,
    conversation_id UNINDEXED,
    kind UNINDEXED,
    content,
    tokenize = 'unicode61 remove_diacritics 2'
);
```

Index only appropriate kinds, initially `text`, `reasoning`, and `code`. Whether reasoning is searchable should be a privacy/product setting; default can exclude reasoning from snippets even if indexed.

Maintain FTS rows transactionally in repository methods or simple, tested triggers. Provide a rebuild command for recovery/migration.

Search results return:

```text
conversation_id
message_id / part_id
rank
sanitized snippet
matched field/kind
```

Do not expose FTS markup directly as HTML.

## Branching model

### Regenerate

Given user message `U1` and assistant answer `A1`:

```text
U1
├─ A1 (original branch)
└─ A2 (regenerated branch)
```

Create a new branch whose fork point is `U1`, then append `A2`. Preserve `A1`.

### Edit user message

Given parent assistant/system message `P` and user message `U1`:

```text
P
├─ U1 -> A1
└─ U2 (edited_from=U1) -> A2
```

Editing creates `U2`; it does not overwrite `U1`.

### Retry failed run

Keep failed run/message status and create a new run linked in generation metadata. Depending on UX, the retry can continue the same branch if no completed child exists or create a branch; define policy explicitly in core.

### Compare responses

Retrieve sibling assistant messages sharing the same parent and render them without mutating branch heads.

Repository methods accept/return domain types, not `sqlx::Row`, JSON API objects, or frontend DTOs.

## Transaction boundaries

Examples that must be atomic:

- create conversation + main branch
- append user message + create pending run
- checkpoint message parts + run sequence
- finalize message + generation metadata + branch head + conversation updated time
- edit message + create branch + update active branch
- delete conversation and derived records
- import one legacy conversation

## Migrations

Use numbered immutable migrations, for example:

```text
0001_initial.sql
0002_fts.sql
0003_provider_sessions.sql
0004_legacy_import_marker.sql
```

Rules:

- migration runs before repositories become available
- each migration is tested from an empty database
- representative old-version upgrade paths are tested
- destructive migrations make a backup or explicit export first
- never edit an already released migration; add a new one
- schema version is observable in diagnostics

## Legacy importer

### Source

Current default:

```text
data/chat_history.db
```

### Mapping

| Legacy | New |
| --- | --- |
| conversation row | workspace default + conversation + `main` branch |
| `conversations.id` | preserve as conversation ID if valid/unique |
| `messages.id` | preserve as message ID if valid/unique |
| role | same normalized role |
| content | `message_parts(kind=text)` |
| thinking_content | additional `message_parts(kind=reasoning)` |
| timestamp | message/part created time |
| model | resolve/create model reference |
| token_count | generation metadata marked estimated/legacy |

Parent IDs are reconstructed in timestamp/row order within the main branch. Record ambiguity if timestamps collide; legacy query already uses `timestamp, rowid` and the importer should preserve that ordering while reading.

### Safety

1. Open legacy DB read-only.
2. Verify expected tables/columns.
3. Back up target DB before import.
4. Import each conversation transactionally.
5. Write source fingerprint and import marker.
6. Re-running is idempotent.
7. Compare counts and hashes of message content.
8. Never delete or mutate source DB automatically.

## Retention and deletion

- Conversation delete cascades durable domain rows.
- Attachment blobs are deleted only when no references remain.
- Credential deletion is handled by auth service, not DB cascade.
- Consider soft-delete/archive for workspaces/conversations before permanent purge.
- Exports must clearly indicate whether reasoning/citations/attachments are included.

## Backup and recovery

- expose “backup database” before destructive migration
- use SQLite online backup API or consistent checkpoint strategy
- validate migration and FTS integrity on startup diagnostics
- recover `running` runs as `interrupted` after unclean shutdown
- offer FTS rebuild without losing source rows

## Tests

Required database tests:

- clean migration to latest
- upgrades from every released schema fixture
- FK/cascade behavior
- branch traversal and sibling responses
- edit/regenerate semantics
- checkpoint/finalize transactions
- FTS insert/update/delete/rebuild
- concurrent reader/writer behavior
- cancellation/failed-run persistence
- legacy import idempotency and content parity
- no credential value in any table
